Заголовок: Мониторинг и бэкап

Сервис чаще умирает тихо: нода легла ночью, у хостинга кончился баланс и сервер выключили, серт (сертификат, файл-подтверждение для шифрованного соединения) протух, БД (база данных, где хранятся все клиенты и ноды) не бэкапилась, а вы узнаёте из потока негатива в боте. Настройка обоих слоёв — монитора и бэкапа — займёт около часа, зато потом падение узнаёте вы, а не клиенты в поддержке. Нужна статья тем, у кого уже есть хотя бы одна панель Remnawave с клиентами; если сервис ещё в разработке, сначала поднимите его, а сюда вернитесь перед первыми продажами.

📖 Незнакомые слова? Все термины простыми словами есть в Словаре терминов.

Что мониторить
Объект	Признак беды	Как
Ноды	offline в панели	Remnawave статус + внешний uptime
Страница подписки	не отвечает → клиенты без конфигов	HTTP-проверка URL подписки
Диск / RAM ноды	переполнение → Xray падает	Мониторинг ресурсов (Beszel)
Баланс хостинга	уйдёт в ноль → сервер выключат	напоминания, авто-пополнение
Домен / сертификат	протух → всё лежит	срок в Cloudflare/certbot, авто-renew
Uptime Kuma + алерты в Telegram

Uptime Kuma — бесплатный веб-сервис мониторинга: сам стучится на ваши адреса по расписанию и шлёт уведомление, если ответа нет. Поднимается за 2 минуты:

bash
docker run -d --restart=always -p 127.0.0.1:3001:3001 \
 -v uptime-kuma:/app/data --name uptime-kuma louislam/uptime-kuma:1

Должно получиться: контейнер поднимется (docker ps покажет uptime-kuma со статусом Up), панель будет слушать порт 3001 только на самом сервере.

Откройте её за reverse-proxy (веб-сервер вроде nginx/Caddy, который проксирует внешние запросы на локальный порт 3001, чтобы не открывать его в интернет напрямую), добавьте мониторы: TCP на ноды (IP:443), HTTP на страницу подписки. В Notifications → Telegram: бот-токен + ваш chat_id (числовой идентификатор чата, куда бот пишет — свой можно узнать у @userinfobot) → при падении прилетит сообщение. Поставьте интервал 60 с и 2–3 ретрая (чтобы не дёргало на моргании).

⚠️ Kuma отвечает только на вопрос «отвечает порт или нет» и краснеет ровно тогда, когда клиенты уже пишут в поддержку. Она не видит, что диск забился логами Xray и до аварии осталось три дня. Второй слой: мониторинг ресурсов изнутри. Читайте: Мониторинг ресурсов: увидеть, что нода умирает, до падения. Нужны оба.

Бэкап БД Remnawave (обязательно)

Нет бэкапа БД = угон/сбой = потеря всех клиентов. PostgreSQL дампится одной командой:

bash
cd /opt/remnawave
docker compose exec -T remnawave-db pg_dump -U postgres postgres > backup-$(date +%F).sql
tar czf conf-$(date +%F).tgz .env docker-compose.yml

Должно получиться: два файла в текущей папке — backup-ДАТА.sql (дамп базы, не должен быть пустым) и conf-ДАТА.tgz (настройки панели).

Авто-бэкап по cron (планировщик заданий Linux, запускает команды по расписанию, ежедневно в 4:00) + выгрузка вне сервера (rclone — консольная утилита для копирования файлов в облако, в S3 или на другой диск):

bash
cat >/etc/cron.d/rw-backup <<'EOF'
0 4 * * * root cd /opt/remnawave && docker compose exec -T remnawave-db pg_dump -U postgres postgres | gzip > /root/backups/db-$(date +\%F).sql.gz
EOF
# выгрузка наружу (настройте rclone заранее):
# rclone copy /root/backups remote:vpnhub-backups

Храните бэкапы в другом месте (другой провайдер/облако). Бэкап на том же сервере, который изъяли/удалили, бесполезен. Держите 7–14 копий.

Восстановление
bash
cd /opt/remnawave
docker compose up -d remnawave-db # поднять только БД
gunzip < /root/backups/db-2026-06-05.sql.gz | \
 docker compose exec -T remnawave-db psql -U postgres postgres # залить дамп
docker compose up -d # поднять панель

Должно получиться: пользователи, ноды и сквады (группы нод, которые панель раздаёт пользователю пакетом) на месте, ноды поднялись online. Регулярно тестируйте восстановление на запасном сервере: «бэкап, который не восстанавливается» = нет бэкапа.

Авто-продление сертификатов
certbot ставит systemd-timer (встроенный планировщик systemd, аналог cron) сам: проверьте systemctl list-timers и найдите в списке certbot.
Для нод за CDN/Reality серт от Let's Encrypt: certbot renew --dry-run раз в квартал для контроля.
Гигиена «не слить деньги»
Удаляйте лишние/выключенные VPS: они тикают по счёту (главный убийца маржи).
Настройте напоминания о балансе хостингов (часть провайдеров шлёт на почту/в ТГ).
Дашборд: одна страница со статусом всех нод + подписки + балансов.
Если не получилось
Симптом	Что проверить	Что сделать
Kuma не открывается в браузере	Слушает ли контейнер порт: docker ps	Порт 3001 привязан только к 127.0.0.1 — заходите через reverse-proxy или SSH-туннель, а не напрямую по IP
Алерты в Telegram не приходят	Токен бота и chat_id в Notifications	Проверьте, что бот не заблокирован и chat_id ваш, а не чужой; отправьте тестовое уведомление кнопкой в настройках
Kuma дёргает алертами на секундных сбоях	Интервал проверки и число ретраев	Поставьте интервал 60 с и 2–3 ретрая, одиночный обрыв не должен считаться падением
pg_dump завершается с ошибкой доступа	Название контейнера БД и пользователя: docker compose ps	Имя контейнера/пользователя может отличаться от remnawave-db/postgres, если меняли docker-compose.yml — подставьте свои
Файл дампа весит несколько байт	Открыт ли файл текстовым редактором — не ошибка ли внутри вместо дампа	Значит pg_dump упал молча, смотрите вывод команды без перенаправления в файл и чините доступ к БД
После восстановления ноды не поднимаются online	Совпадают ли SECRET_KEY нод в восстановленной БД с тем, что реально прописан на нодах	Если ключи разъехались, перевыпустите их в панели и обновите на нодах
Чего это не даёт
Kuma не видит здоровье ноды изнутри — она проверяет только «отвечает порт или нет». Диск и память смотрит отдельный слой, см. Мониторинг ресурсов.
Бэкап БД не спасает от блокировки адреса — сервис восстановится, но клиентам всё равно нужен рабочий адрес ноды.
Локальный бэкап на том же сервере не защита — при изъятии или потере сервера пропадёт вместе с ним, копия обязана лежать в другом месте.
Автопродление сертификата не проверяет само себя — если DNS или порт 80 заняты в момент продления, certbot renew тихо не сработает, нужен внешний контроль (например, монитор срока в Kuma).
Ничего из этого не восстановит клиентов, если утеряны ключи/UUID — бэкап БД для этого и нужен, без него ноды поднимутся, а подписки — нет.

Связано: «Защита панели» (бэкап до правок), «Заблокировали IP?» (реакция на падение).
