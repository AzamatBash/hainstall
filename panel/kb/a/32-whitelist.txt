Заголовок: Свой белый вход: как поднять и что отдать клиенту

🧭 Цикл про белые списки. Обзор: чем закрывать отключения · Настройка своего белого входа · Проверка адреса перед оплатой · Репутация адреса и капчи · Кабинет бота за CDN

При веерных отключениях оператор оставляет доступ к списку разрешённых ресурсов и закрывает остальное. Обычный VPS в этот список не входит, поэтому во время отключения он молчит.

Здесь собрана рабочая схема: российский сервер с белым адресом принимает подключения и передаёт их дальше, на вашу заграничную ноду. Клиент видит российский адрес, сайты видят заграничный.

Сайты видят адрес заграничной ноды. Оператор видит только соединение к российскому адресу.

Ключи и сертификаты остаются на заграничной ноде. Российский сервер работает на транспортном уровне: принимает соединение, смотрит имя домена в приветствии клиента и передаёт поток дальше байт в байт. Расшифровывать там нечего, поэтому изъятие входа не отдаёт ваши ключи.

Что понадобится
Российский сервер с белым адресом. Проверить адрес до оплаты — в статье Белый IP: как проверить адрес до оплаты. Хватит одного ядра и гигабайта памяти: HAProxy не расшифровывает трафик и почти не ест ресурсы.
Заграничная нода с поднятым Reality. Как поднять — VLESS-TCP-Reality.
Домен, который вы отдадите клиентам. Годится и поддомен: он нужен, чтобы вход различал арендаторов по имени.
Шаг 1. Убедитесь, что адрес правда белый

Проверяйте с мобильного интернета, а не из дома: у операторов свои списки.

bash
nc -vz БЕЛЫЙ_IP 443

Должно появиться succeeded. Если порт молчит, дальше идти бессмысленно: либо адрес не в списке, либо на сервере ещё ничего не слушает.

Шаг 2. Поставьте HAProxy

На российском сервере, под root:

bash
apt update && apt -y install haproxy && haproxy -v

Версия должна быть 2.8 или новее. На Ubuntu 22.04 в стандартном репозитории лежит 2.4, которая уже снята с поддержки — берите пакет из репозитория проекта.

Шаг 3. Конфиг входа

Замените vpn.example.com на свой домен, а 203.0.113.10 — на адрес заграничной ноды.

bash
cat >/etc/haproxy/haproxy.cfg <<'CFG'
global
 log /dev/log local0
 maxconn 20000
 user haproxy
 group haproxy
 daemon

defaults
 mode tcp
 option tcplog
 timeout connect 5s
 timeout client 4h
 timeout server 4h

frontend white_in
 bind:443
 tcp-request inspect-delay 5s
 tcp-request content accept if { req_ssl_hello_type 1 }
 use_backend node_eu if { req_ssl_sni -i vpn.example.com }
 default_backend node_eu

backend node_eu
 server eu1 203.0.113.10:443 check
CFG
haproxy -c -f /etc/haproxy/haproxy.cfg

Последняя команда проверяет конфиг и печатает Configuration file is valid. Не применяйте конфиг, пока не увидите эту строку: с ошибкой служба не поднимется, и вход останется лежать.

Длинные таймауты стоят не просто так. По умолчанию HAProxy рвёт соединение через минуту простоя, и клиенты жалуются, что «отваливается, когда не пользуюсь».

Запуск:

bash
systemctl enable --now haproxy && systemctl status haproxy --no-pager | head -5

В выводе должно быть active (running).

Шаг 4. Откройте порт
bash
ufw allow 443/tcp && ufw reload && ss -tlnp sport =:443

ss должен показать haproxy. Если там nginx или Caddy, сначала освободите порт: одновременно 443 держит только один процесс.

⚠️ Грабля, которая роняет весь сервер. Не занимайте под клиентов порты из диапазона, который ядро раздаёт исходящим соединениям (обычно 32768–60999). Рано или поздно система выдаст тот же порт своему соединению, и HAProxy не сможет подняться. Проверить диапазон: sysctl net.ipv4.ip_local_port_range. Нужные порты резервируйте через net.ipv4.ip_local_reserved_ports.

Шаг 5. Направьте домен на белый адрес

В DNS создайте A-запись: vpn.example.com → белый адрес, режим «только DNS» без проксирования. Проверьте:

bash
dig +short vpn.example.com

Ответ должен совпадать с адресом входа.

Шаг 6. Хост в панели Remnawave

Клиенту отдаётся не адрес ноды, а адрес входа. В панели откройте Хосты → Новый хост.

Форма нового хоста: инбаунд берём с заграничной ноды, а адрес и порт указываем от белого входа.

Что вписать:

Поле	Значение	Почему так
Инбаунд	тот, что поднят на заграничной ноде	клиент шифруется с нодой, вход только передаёт поток
Адрес	vpn.example.com	домен ведёт на белый адрес; менять вход потом можно правкой DNS
Порт	443	тот, что слушает HAProxy
Теги	по вашему усмотрению	клиенту не видны
Ноды	заграничная нода	поле влияет только на отображение в панели

Имя домена в поле адреса и в маскировке инбаунда должно совпадать: по нему вход и выбирает, куда отправить соединение.

Шаг 7. Проверьте по пути клиента

Сначала с любого чужого сервера — дошло ли до ноды:

bash
nc -vz vpn.example.com 443

Затем на самом входе посмотрите, идут ли соединения дальше:

bash
ss -tnp state established '( dport =:443 )' | head

Последняя проверка — подключение настоящим клиентом с мобильного интернета. Откройте сервис проверки адреса: он должен показать страну заграничной ноды, а не Россию.

Если не получилось
Симптом	Что проверить	Что сделать
Служба не стартует	haproxy -c -f /etc/haproxy/haproxy.cfg	Команда назовёт строку с ошибкой. Пока конфиг не проходит проверку, запускать бесполезно
Порт занят	ss -tlnp sport =:443	Освободите 443 от nginx или Caddy, либо разнесите их по разным серверам
Клиент подключается, интернета нет	Доступна ли нода со входа: nc -vz АДРЕС_НОДЫ 443	Вход исправен, проблема на втором плече. Смотрите ноду и её файрвол
Соединение рвётся при простое	Таймауты в конфиге	Поднимите timeout client и timeout server до нескольких часов
Работает с домашнего интернета, не работает с мобильного	Адрес входа	Скорее всего адрес не в белом списке этого оператора. Проверьте у второго оператора
Всё поднялось, потом резко встало у всех	Живой ли вход: nc -vz БЕЛЫЙ_IP 443 с чужой сети	Молчат все порты — адрес заблокировали. Меняйте вход, на сервере чинить нечего
После обновления клиенты отвалились	Чем применяли изменения	Применяйте systemctl reload haproxy, а не restart: reload доживает открытые соединения
Крупные загрузки встают, мелочь идёт	Размер пакета	Лишнее плечо отъедает место в пакете. Уменьшайте MTU по цепочке
Чего эта схема не даёт
Вход блокируют так же, как обычный сервер. Белый адрес живёт дольше, но не вечно: держите второй вход в другой сети.
Маршрутизации по доменам нет. HAProxy не читает трафик, поэтому «это напрямую, а это через VPN» здесь не настроить, только целиком.
UDP не проходит. Hysteria через эту схему не пойдёт, для неё нужен отдельный проброс.
Вход знает адрес вашей ноды. Спрятать и его можно только ещё одним плечом.
Через ваш белый адрес пойдёт чужой трафик. Закройте почтовые порты и ограничьте частоту новых соединений, иначе получите жалобу хостеру.
