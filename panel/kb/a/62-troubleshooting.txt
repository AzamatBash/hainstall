Заголовок: Диагностика «не работает»: где искать поломку

Клиент пишет «не подключается». Не угадывайте: идите по цепочке клиент → подписка → нода → порт → протокол → роутинг и находите слой, где рвётся. Гадание и наобум-советы вроде «переустановите приложение» тратят время саппорта и злят клиента, который просто хочет, чтобы работало.

📖 Незнакомые слова? Все термины простыми словами есть в Словаре терминов.

Сначала 3 вопроса клиенту
Оператор и город (мобильный/домашний: у мобильных DPI — Deep Packet Inspection, система анализа трафика оператора, которая ищет признаки VPN — строже).
Приложение (Happ/Hiddify/v2rayNG) и какой сервер выбран.
Что именно не работает: вообще нет связи / только некоторые сайты / медленно / РФ-сайт не открывается.

Это сразу сужает поиск.

Быстрая таблица «симптом → причина»
Симптом	Чаще всего виновато	Что сделать
Вообще не подключается (у всех)	нода offline / порт закрыт / истёк серт	поднять контейнер/порт, при протухшем серте — certbot renew
Не подключается у одного клиента	его подписка не обновлена / устройство-лимит (hwidDeviceLimit, лимит по отпечатку устройства) / не туда выбрал сервер	обновить подписку в приложении, снять лишнее устройство или сменить сервер
«не видит сервер» в приложении	inbound не добавлен в сквад юзера	добавить inbound в сквад юзера (Internal Squads)
Работает на Wi-Fi, не на мобильном	DPI/«белые списки» оператора	переключить на WL-вход/каскад
Подключается, но сайты не грузятся	роутинг / DNS клиента	сменить DNS на 8.8.8.8 DoH (не Cloudflare)
РФ-сайт/банк не открывается	нет RU-direct роутинга (правило: российские адреса идут напрямую, минуя VPN)	настроить RU-direct роутинг
Скачивание идёт, а YouTube висит	застрявший QUIC (быстрый протокол поверх UDP, на нём работает YouTube) → блок UDP/443 на ноде	разобраться с блоком UDP/443 на ноде
Капчи, «VPN detected»	грязный IP ноды (репутация адреса испорчена массовым использованием) → замена из запаса	сменить IP ноды, сгоревший — в blocklist (чёрный список)
Проверки на сервере (по слоям)

1. Нода жива и порт открыт:

bash
# с любой машины:
nc -vz НОДА_IP 443 # порт отвечает?
# на ноде:
docker ps | grep remnanode # контейнер up?
docker logs --tail 50 remnanode # ошибки Xray?

2. Сертификат (для TLS-инбаундов):

bash
echo | openssl s_client -connect НОДА:443 -servername ВАШ_SNI 2>/dev/null | openssl x509 -noout -dates -issuer

Протух/неверный домен → перевыпустить (certbot renew).

3. Reality: совпадение параметров. 90% «не подключается на Reality» это рассинхрон Host ↔ config: - Public Key в Host = publicKey из пары (а в конфиге privateKey). - Short ID в Host = один из shortIds конфига (или оба пусты). - SNI в Host = serverNames конфига. - Fingerprint задан (firefox/qq). Проверьте «открывается ли https://ВАШ_SNI» в браузере: для self-steal должен открыться сайт-обманка.

4. Сквад. Inbound включён на ноде, Host создан, но юзер не видит? Зайдите Internal Squads и убедитесь, что нужный inbound отмечен в его скваде. Формула: доступ = (inbounds в сквадах юзера) ∩ (inbounds на ноде) ∩ (видимые хосты).

5. Подписка отвечает:

bash
curl -s -o /dev/null -w "%{http_code}\n" https://sub.ВАШ_ДОМЕН/КОРОТКИЙ_UUID

Не 200 → проблема страницы подписки / reverse-proxy.

Что сделать клиенту (если сервер исправен)
Обновить подписку в приложении.
Сменить сервер (другой из списка / «Авто»).
DNS → https://8.8.8.8/dns-query (не Cloudflare).
Вкл/выкл «обход для России».
Переустановить профиль из ссылки.
Если массово легло
Подтвердить блок с мобильного оператора (не только дома).
Перекинуть на резерв (каскад/WL/CDN, обычно автоматом).
Сменить IP ноды из запаса, сгоревший → blocklist.
Сменить SNI/донор/fingerprint.
Написать статус в канал: молчание = отток.
Чего эта диагностика не даёт
Не находит проблему за вас: если ни один слой цепочки не подтверждает поломку, а клиент всё равно жалуется, дело может быть в его локальной сети или у оператора, а не на вашей стороне.
Проверки (nc, curl, openssl) показывают состояние в момент запуска: на нестабильном канале одна успешная проверка не гарантирует, что через минуту всё так же будет работать.
Таблица «симптом → причина» — это самые частые случаи, а не исчерпывающий список: бывают и редкие сочетания нескольких причин сразу.
При массовом сбое разбор по одному клиенту не масштабируется: сначала переключайтесь на резерв и пишите статус в канал, а искать первопричину — уже параллельно.

Связано: «Все рабочие конфиги» (привязка Host), «Заблокировали IP?», «Маршрутизация», «Клиентские приложения».
