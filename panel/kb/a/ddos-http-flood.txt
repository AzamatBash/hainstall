Заголовок: HTTP-флуд: как 40 запросов в секунду положили сайт и что с этим сделали

17 октября в 17:43 по Москве сайт перестал открываться и пролежал около двадцати минут. Это была DDoS-атака, HTTP-флуд по главной странице. Атака была небольшой, но сайт она уронила. Разбираем честно: почему так вышло, как мы нашли причину и что поставили, чтобы это не повторилось. Всё это применимо к сайту или панели вашего VPN-сервиса.

Что произошло
17:43. На главную пошли запросы примерно с 80 серверов в облаках: DigitalOcean, Azure, Google Cloud. Около 40 запросов в секунду. Живые люди так не ходят: у всех один и тот же урезанный заголовок браузера без версии, ни одного запроса к картинкам и стилям, только главная.
17:44. Веб-сервер Caddy, который стоит перед сайтом, начал отвечать ошибкой 502, а через минуту перестал отвечать совсем.
17:59. Перезапустили Caddy, и флуд вернулся сразу: на пике 7 130 запросов за минуту.
18:04. Забанили 44 самых активных адреса и снова перезапустили Caddy.
18:06. Включили отдачу главной готовым файлом. С этого момента сайт держится.
Почему хватило 40 запросов в секунду

Для DDoS это очень мало: обычный сервер отдаёт тысячи запросов в секунду. Атака сработала из-за трёх наших слабостей.

Главная собиралась заново на каждый запрос. Python рендерил страницу, и без прогретого кэша это занимало 5–8 секунд. Вдобавок на каждый показ в базу SQLite писалась строка аналитики.
Сайт работал одним процессом. Python в одном процессе использует одно ядро процессора из четырёх. Десятки тяжёлых запросов в секунду забивают его целиком, и ждут все: и гости, и те, кто в этот момент оплачивает подписку.
Зависший веб-сервер никто не перезапускал. Caddy копил висящие запросы, раздулся до 1,5 ГБ памяти и встал. Но процесс оставался жив, поэтому для systemd всё было в порядке.
Как мы нашли причину

Первым делом проверяем по слоям, где именно застревает запрос.

bash
# приложение отвечает напрямую, мимо веб-сервера?
curl -s -o /dev/null -w '%{http_code} %{time_total}\n' http://127.0.0.1:8000/robots.txt

# а через веб-сервер? (с самого сервера, мимо DNS)
curl -s -o /dev/null -m 10 -w '%{http_code} %{time_total}\n' \
 --resolve example.com:443:127.0.0.1 https://example.com/robots.txt

У нас приложение ответило за 12 миллисекунд, а запрос через Caddy висел до таймаута. Значит, проблема в веб-сервере, а не в коде.

Дальше смотрим журнал веб-сервера: кто и куда стучится.

bash
# топ адресов за последние 10 минут (журнал Caddy в формате JSON)
jq -r 'select(.ts > (now - 600)) |.request.client_ip' /var/log/caddy/access.log | sort | uniq -c | sort -rn | head

# топ путей со статусами
jq -r 'select(.ts > (now - 600)) | "\(.status) \(.request.uri)"' /var/log/caddy/access.log | sort | uniq -c | sort -rn | head

Признаки флуда: один и тот же путь, одинаковый заголовок браузера, адреса облачных провайдеров и никаких запросов к картинкам и стилям.

⚠️ kill -QUIT у Caddy не даёт дамп горутин, как у обычных программ на Go: Caddy сам обрабатывает этот сигнал. Если он завис, перезапускайте так: timeout 25 systemctl restart caddy || systemctl kill -s KILL caddy.

Что сделали в первые минуты
Перезапустили веб-сервер. Это возвращает сайт, но ненадолго, если атака продолжается.
Забанили самых активных. Отобрали адреса, которые за 15 минут сделали больше сотни запросов на главную без входа в аккаунт, и отправили их в бан fail2ban на час.
bash
fail2ban-client set <имя-джейла> banip 203.0.113.10

Баньте только явных нарушителей. Мобильные операторы выводят в интернет тысячи людей через один адрес, и широкий бан отрежет настоящих клиентов.

Что поставили, чтобы это не повторилось

1. Главная для гостей — готовым файлом

Гостевая главная одинакова для всех. Мы это проверили: сравнили страницу для разных браузеров и языков, она совпала до байта. Значит, её не нужно собирать на каждый запрос. Раз в две минуты таймер забирает страницу у приложения и кладёт на диск, а Caddy отдаёт файл сам.

caddyfile
@guesthome {
 path /
 method GET HEAD
 expression `{query} == ""`
 not header_regexp Cookie (^|;\s*)session=
 file {
 root /var/www/guest-home
 try_files /index.html
 }
}
handle @guesthome {
 root * /var/www/guest-home
 rewrite * /index.html
 file_server
}

Вошедшие пользователи (кука session) идут в приложение, как раньше. Если файла почему-то нет, запрос тоже уходит в приложение.

Снимок обновляет простой скрипт по таймеру systemd:

bash
#!/bin/bash
# /usr/local/bin/guest-home.sh — раз в 2 минуты
TMP=$(mktemp /var/www/guest-home/.index.XXXXXX)
code=$(curl -s -m 30 -o "$TMP" -w '%{http_code}' -H 'Host: example.com' http://127.0.0.1:8000/)
if [ "$code" = 200 ] && grep -q '</html>' "$TMP"; then
 chmod 644 "$TMP" && mv -f "$TMP" /var/www/guest-home/index.html
else
 rm -f "$TMP" # прошлый снимок остаётся
fi

2. Кэш остальных публичных страниц

Статьи, тарифы, новости и лендинги продуктов для гостей тоже одинаковы. Перед ними мы поставили nginx с кэшем на минуту. Главное в настройке — три строки:

proxy_cache_lock: на промахе кэша в приложение идёт один запрос, а не тысяча одновременных;
proxy_cache_use_stale: если приложение тормозит или упало, гость получает прошлую копию страницы;
proxy_cache_background_update: копия обновляется фоном, гость не ждёт.
nginx
proxy_cache_path /var/cache/nginx/site keys_zone=site:20m max_size=512m inactive=30m use_temp_path=off;
limit_req_zone $binary_remote_addr zone=perip:10m rate=10r/s;

server {
 listen 127.0.0.1:8080;
 set_real_ip_from 127.0.0.1;
 real_ip_header X-Real-IP;

location / {
 limit_req zone=perip burst=40 nodelay; # один адрес не зальёт даже кэш
 proxy_pass http://127.0.0.1:8001;
 proxy_set_header Host $host;
 proxy_set_header Cookie ""; # гостю куки не нужны, и чужое в кэш не попадёт
 proxy_cache site;
 proxy_cache_key "$host$request_uri";
 proxy_cache_valid 200 60s;
 proxy_ignore_headers Cache-Control Expires;
 proxy_cache_lock on;
 proxy_cache_use_stale error timeout updating http_500 http_502 http_503 http_504;
 proxy_cache_background_update on;
 }
}

nginx по умолчанию не кэширует ответы с Set-Cookie, и это правильно. Если ваше приложение ставит гостю куку на каждой странице, кэш работать не будет, пока вы это не уберёте (смотрите пункт 4).

3. Публичные страницы — в отдельном процессе

Самое важное для денег. В нашем приложении живут фоновые задачи: сверка платежей, уведомления, прогрев кэшей. Поэтому его нельзя просто запустить в несколько процессов (--workers 4): каждая копия запустит свою сверку платежей, и они пойдут одновременно.

Мы сделали по-другому: запустили второй экземпляр приложения с переменной окружения, которая выключает все фоновые задачи. Он отдаёт гостям только публичные страницы, через кэш. Основной процесс с оплатами и кабинетами остался один и флуда больше не видит.

ini
# /etc/systemd/system/site-public.service
[Service]
# в коде: if not os.getenv("APP_PUBLIC"): start_background_jobs
Environment=APP_PUBLIC=1
ExecStart=/opt/app/.venv/bin/python -m uvicorn app.main:app --host 127.0.0.1 --port 8001 --workers 2
Restart=always
MemoryMax=1500M

4. Аналитика без записи на сервере

Раньше каждый показ страницы писал строку в базу и ставил гостю куку. Это мешает кэшу, а под флудом превращается в тысячи записей в SQLite. Теперь страница из кэша сама сообщает о просмотре из браузера:

html
<script>
navigator.sendBeacon('/stats/view', JSON.stringify({
 p: location.pathname, r: document.referrer, q: location.search
}));
</script>

Бонус: боты, которые флудят без JavaScript, этот сигнал не шлют, так что аналитика стала чище.

5. Сторож веб-сервера

Раз в минуту таймер проверяет сайт через Caddy с самого сервера. Если три проверки подряд не прошли, а приложение напрямую отвечает, сторож перезапускает Caddy и пишет нам в Telegram.

bash
#!/bin/bash
# /usr/local/bin/caddy-watchdog.sh — раз в минуту
ST=/run/caddy-watchdog.fails
code=$(curl -s -o /dev/null -m 8 --resolve example.com:443:127.0.0.1 -w '%{http_code}' https://example.com/robots.txt)
if [ "$code" = 200 ]; then echo 0 > $ST; exit 0; fi
n=$(( $(cat $ST 2>/dev/null || echo 0) + 1 )); echo $n > $ST
[ $n -lt 3 ] && exit 0
# лежит само приложение? тогда дело не в Caddy, его не трогаем
[ "$(curl -s -o /dev/null -m 8 -w '%{http_code}' http://127.0.0.1:8000/robots.txt)" = 200 ] || exit 1
timeout 25 systemctl restart caddy || systemctl kill -s KILL caddy
echo 0 > $ST

Что получилось

Мы проверили защиту нагрузкой: 8 секунд флуда по кэшу с двух тысяч разных адресов. Сервер отдал больше 2 000 запросов в секунду без единой ошибки, это в 50 раз больше, чем во время атаки. Основной процесс всё это время отвечал за 60 миллисекунд.

Чего это не закрывает

Всё, что выше, защищает от HTTP-флуда, то есть от атак на само приложение. Против объёмных атак, когда в сервер льют гигабиты мусорного трафика, настройки на сервере не помогут: канал забивается раньше, чем пакеты доходят до Caddy. Такое фильтруют только снаружи.

Cloudflare — самый простой вариант, но из России он работает с перебоями, и часть ваших клиентов может не открыть сайт.
DDoS-Guard, StormWall — фильтрация, которая нормально работает в России.
Защита у хостера. Например, у Timeweb Cloud защита L3/L4 и L7 стоит от 550 ₽ в месяц при среднем входящем трафике до 1 Мбит/с, но только для серверов в Москве и Санкт-Петербурге, и при подключении меняется IP сервера (документация Timeweb Cloud).

После подключения внешней защиты смените IP сервера: старый адрес атакующие уже знают и могут бить в него напрямую, в обход фильтра. И не держите на одном адресе сайт и критичные сервисы: бота, панель, сервер лицензий.

Как защитить ноды, панель и подписку от DDoS и абуза, разбираем в отдельной статье: DDoS и абуз: защита нод, панели и подписки.

Чек-лист для вашего сайта или панели
Гостевые страницы отдаются из кэша, а не собираются на каждый запрос
Кэш умеет отдавать прошлую копию, когда приложение тормозит
Есть лимит запросов с одного адреса
Публичные страницы и фоновые задачи с деньгами работают в разных процессах
Аналитика не пишет в базу на каждый показ
Веб-сервер проверяет сторож и сам перезапускает при зависании
