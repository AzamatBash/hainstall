Заголовок: Логи и S3-хранилище — собрать, сохранить, найти клиента по жалобе

Логи нужны в двух случаях, и оба случаются внезапно. Первый — жалоба хостера (abuse, письмо «с вашего IP шёл спам / скан портов / торрент, ответьте за 24 часа»): без логов вы не узнаете, какой клиент это делал, и хостер просто заблокирует сервер. Второй — «у клиента не работает»: по логу видно, доходит ли он до ноды вообще. Держать логи на самой ноде нельзя: они забивают диск (почему ноды умирают от логов) и пропадают вместе с сервером. Поэтому схема такая: нода пишет лог → logrotate режет его на сжатые куски → раз в час куски уезжают в S3 (облачное хранилище файлов, о нём ниже) зашифрованными → через 30 дней удаляются сами. Туда же складываются бэкапы панели. Настройка — около 40 минут на первую ноду и 5 минут на каждую следующую.

📖 Незнакомые слова? Все термины простыми словами есть в Словаре терминов.

Что и сколько хранить

Access-лог (журнал подключений: время, IP клиента, куда он ходил, кто он в панели) — это персональные данные ваших клиентов. Храните ровно столько, сколько нужно для разбора жалоб, и закрывайте доступ.

Лог	Что в нём	Нужен для	Срок
access.log Xray	каждое подключение: время, IP, адрес назначения, пользователь	жалобы хостера, поиск нарушителя	14–30 дней
error.log Xray	ошибки ядра, отказы рукопожатия	«у клиента не работает»	7 дней
логи контейнеров (docker logs)	старт/падения ноды и панели	разбор аварий	на сервере, с ротацией
бэкапы БД панели	все клиенты, ноды, ключи	восстановление после потери сервера	30 дней + месячные копии

⚠️ Если access-лог вам не нужен (жалоб не бывает, лимит устройств по IP не используете), его разумнее не включать вовсе: нет данных — нечего утечь и нечему забить диск. Error-лог с уровнем warning нужен всем.

Шаг 1. Включить логи на ноде Remnawave

Нода Remnawave работает в Docker-контейнере, и лог надо вывести из контейнера в папку на сервере. В docker-compose.yml ноды (обычно /opt/remnanode/docker-compose.yml) добавьте в сервис remnanode строку в volumes: (подключение папки сервера внутрь контейнера):

yaml
 volumes:
 - '/var/log/remnanode:/var/log/remnanode'

Затем в панели: Config Profiles → профиль этой ноды → секция log в конфиге Xray:

json
"log": {
 "error": "/var/log/remnanode/error.log",
 "access": "/var/log/remnanode/access.log",
 "loglevel": "warning"
}

Создайте папку и перезапустите ноду:

bash
mkdir -p /var/log/remnanode
cd /opt/remnanode && docker compose up -d

Должно получиться: через минуту-две в /var/log/remnanode/ появятся access.log и error.log, а tail -n 3 /var/log/remnanode/access.log покажет строки вида 2026/09/24 14:25:31 from 5.6.7.8:51234 accepted tcp:example.com:443 [...] email:.... После email: — метка пользователя из панели, по ней вы и найдёте клиента.

Для 3x-ui путь к логам задаётся в настройках Xray самой панели (секция log того же вида), дальше всё одинаково.

Шаг 2. Ротация: резать лог на сжатые куски

logrotate (стандартная утилита Linux, которая по расписанию переименовывает, сжимает и удаляет старые логи) уже стоит почти везде. Положите правило:

bash
apt install -y logrotate
cat >/etc/logrotate.d/remnanode <<'EOF'
/var/log/remnanode/*.log {
 daily
 maxsize 200M
 rotate 7
 compress
 dateext
 dateformat -%Y%m%d-%H%M%S
 missingok
 notifempty
 copytruncate
}
EOF
logrotate -vf /etc/logrotate.d/remnanode

Должно получиться: рядом с access.log появится сжатый кусок access.log-ДАТА-ВРЕМЯ.gz, а сам access.log начнётся заново с нуля.

copytruncate обязателен: Xray держит файл открытым и не умеет переоткрывать его, без этой строки он продолжит писать в уже удалённый файл, и место не освободится.
maxsize 200M режет лог раньше суток, если он растёт быстро, но только когда logrotate запускается. Обычно он запускается раз в сутки, поэтому для загруженной ноды запускайте это правило каждый час (строка в cron в шаге 5).
Логи самих контейнеров Docker по умолчанию не режутся вообще — как это лечится, в статье про умирающие ноды.
Шаг 3. S3-хранилище: что это и где взять

S3 — облачное хранилище файлов, которое работает по протоколу Amazon S3. Его продают почти все облака, платите за гигабайты хранения (сотни мегабайт сжатых логов в месяц обходятся в рубли). Файлы лежат в бакете (bucket — именованный контейнер для файлов, как папка верхнего уровня), доступ — по паре ключей Access Key + Secret Key, адрес API — endpoint.

Провайдер	endpoint	region	Где взять ключи
Yandex Object Storage	https://storage.yandexcloud.net	ru-central1	сервисный аккаунт → статический ключ доступа
Selectel S3	https://s3.ru-1.storage.selcloud.ru	ru-1	сервисный пользователь → S3-ключ
Timeweb Cloud S3	https://s3.twcstorage.ru	ru-1	бакет → вкладка «Дашборд»
Cloudflare R2	https://ID_АККАУНТА.r2.cloudflarestorage.com	auto	R2 → Manage API tokens
Backblaze B2	https://s3.РЕГИОН.backblazeb2.com	регион бакета	App Keys

⚠️ Хранилище — у другого провайдера, не там, где ноды и панель. Если аккаунт хостера заблокируют или сервер изымут, копия должна остаться. Адреса и регионы у провайдеров иногда меняются — перед настройкой сверьте их в кабинете: раздел S3 / «Объектное хранилище» → «Подключение».

В кабинете провайдера: 1. Создайте приватный бакет (не публичный!), например vpn-archive — в нём будут и логи, и бэкапы. 2. Создайте ключ, у которого доступ только к этому бакету. Если провайдер умеет роли, ноде хватит права загрузки без права удаления (в Yandex — роль storage.uploader): тогда тот, кто взломает ноду, не сможет стереть логи. 3. Если есть настройка «Жизненный цикл» (lifecycle) — сразу поставьте удаление файлов старше 30 дней. Нет такой настройки — сделаем чисткой по расписанию в шаге 5.

Шаг 4. rclone: подключить хранилище к серверу

rclone — консольная программа для копирования файлов в облака. Ставим и подключаем хранилище (ключи вводятся с клавиатуры, чтобы не остаться в истории команд):

bash
curl -fsSL https://rclone.org/install.sh | bash
read -rp "Access Key: " AK; read -rsp "Secret Key: " SK; echo
rclone config create s3 s3 provider=Other env_auth=false \
 access_key_id="$AK" secret_access_key="$SK" \
 endpoint=https://storage.yandexcloud.net region=ru-central1 \
 acl=private no_check_bucket=true
unset AK SK

Для Cloudflare R2 замените provider=Other на provider=Cloudflare, endpoint и region=auto — из таблицы выше.

Теперь шифрование: rclone будет шифровать файлы на сервере до отправки, и в облаке они лежат нечитаемыми — даже для самого провайдера. Пароль придумайте сами и сразу сохраните в менеджер паролей: без него логи и бэкапы не расшифровать никак.

bash
read -rsp "Пароль шифрования: " CP; echo
rclone config create s3c crypt remote=s3:vpn-archive password="$CP" \
 filename_encryption=off --obscure
unset CP
chmod 600 ~/.config/rclone/rclone.conf

Проверка — записать, прочитать, удалить тестовый файл:

bash
echo test | rclone rcat s3c:_check/hello.txt
rclone cat s3c:_check/hello.txt
rclone delete s3:vpn-archive/_check

Должно получиться: вторая команда напечатает test. В кабинете провайдера в бакете будет лежать _check/hello.txt.bin — это и есть зашифрованная копия (с ключом «только загрузка» третья команда выдаст отказ — это нормально, удалите файл в кабинете).

filename_encryption=off оставляет имена файлов читаемыми: по ним удобно искать нужную дату. Содержимое всё равно зашифровано.
Работайте всегда через s3c: (с шифрованием). Через s3: файлы зальются открытыми.
Шаг 5. Отправка по расписанию

Одна строка режет логи каждый час, вторая отправляет готовые сжатые куски в хранилище. rclone copy не трогает то, что уже загружено, поэтому повтор безопасен:

bash
cat >/etc/cron.d/remnanode-logs <<'EOF'
5 * * * * root /usr/sbin/logrotate /etc/logrotate.d/remnanode
20 * * * * root /usr/bin/rclone copy /var/log/remnanode s3c:logs/$(hostname) --include "*.gz" --max-age 3d --log-file /var/log/rclone-logs.log --log-level NOTICE
EOF

Должно получиться: через час rclone ls s3c:logs/$(hostname) покажет файлы access.log-ДАТА-ВРЕМЯ.gz. Локально на ноде остаётся 7 последних кусков (строка rotate 7), старые logrotate удалит сам.

Срок хранения в облаке, если у провайдера нет «Жизненного цикла». Запускайте на одном сервере (например, на панели) с ключом, у которого есть право удаления:

bash
cat >/etc/cron.d/s3-retention <<'EOF'
40 5 * * * root /usr/bin/rclone delete s3:vpn-archive/logs --min-age 30d --log-file /var/log/rclone-retention.log --log-level NOTICE
45 5 * * * root /usr/bin/rclone delete s3:vpn-archive/backups/panel --min-age 60d --log-file /var/log/rclone-retention.log --log-level NOTICE
EOF

Должно получиться: логи старше 30 дней и ежедневные бэкапы старше 60 дней исчезают из бакета сами. Месячные копии (backups/monthly, шаг 6) чистка не трогает.

Шаг 6. Бэкапы панели — туда же

В «Мониторинге и бэкапе» дамп базы делается каждую ночь, а выгрузка наружу оставлена «на потом». Вот она. На сервере с панелью (rclone настроен так же, как в шаге 4):

bash
mkdir -p /root/backups
cat >/etc/cron.d/rw-backup <<'EOF'
0 4 * * * root cd /opt/remnawave && docker compose exec -T remnawave-db pg_dump -U postgres postgres | gzip > /root/backups/db-$(date +\%F).sql.gz && tar czf /root/backups/conf-$(date +\%F).tgz .env docker-compose.yml
30 4 * * * root /usr/bin/rclone copy /root/backups s3c:backups/panel --max-age 2d && find /root/backups -type f -mtime +7 -delete
0 5 1 * * root /usr/bin/rclone copy /root/backups s3c:backups/monthly --max-age 1d
EOF

Должно получиться: утром в rclone ls s3c:backups/panel есть свежие db-ДАТА.sql.gz и conf-ДАТА.tgz, первого числа копия ложится ещё и в monthly.

В conf-*.tgz лежит .env панели — пароли и секреты. Поэтому только через s3c:, с шифрованием.
Месячные копии в чистку не попадают нарочно: если ночной бэкап тихо сломается, через 60 дней чистка удалит последние ежедневные копии, а месячные останутся.
Чтобы узнать о сломанном бэкапе сразу, добавьте в Uptime Kuma монитор типа Push и допишите в конец строки 30 4 * * *: && curl -fsS -m 10 "https://ВАШ-KUMA/api/push/ТОКЕН?status=up" >/dev/null. Не пришёл сигнал за сутки — Kuma напишет в Telegram.

Восстановление из облака:

bash
rclone ls s3c:backups/panel | sort -k2 | tail -4 # последние копии
rclone copy s3c:backups/panel/db-2026-09-23.sql.gz /root/restore/

Дальше — как в разделе «Восстановление» статьи про бэкап.

Шаг 7. Пришла жалоба: найти клиента за пять минут

В письме хостера есть время (часто в UTC), ваш IP (значит, какая нода) и адрес жертвы (куда шли подключения). Скачивать ничего не нужно, rclone читает прямо из облака:

bash
rclone ls s3c:logs/nl-node1 | grep 20260923 # куски за нужные сутки
rclone cat s3c:logs/nl-node1/access.log-20260923-050001.gz | zcat \
 | grep "2026/09/23 14:2" | grep "203.0.113.7" | head

Должно получиться: строки подключений к адресу из жалобы в указанные минуты, в конце каждой — email: с меткой пользователя. Находите его в панели и решаете: предупредить, ограничить, отключить. Хостеру отвечаете, что нарушитель найден и отключён, — обычно этого достаточно.

Время в логе — по часам контейнера, обычно это UTC. Если в жалобе московское время, отнимите 3 часа.
Если за нужный час ничего нет — посмотрите локальные свежие куски на самой ноде: zcat /var/log/remnanode/access.log-*.gz | grep..., последний час ещё не уехал в облако.
Если не получилось
Симптом	Что проверить	Что сделать
access.log не появляется	Есть ли строка volumes в compose ноды и применён ли профиль к этой ноде	Добавьте volume, сохраните профиль в панели, docker compose up -d в папке ноды
Файл есть, но пустой	loglevel и путь в секции log	Путь внутри контейнера должен совпадать с правой частью volume — /var/log/remnanode/...
После ротации место на диске не освобождается	lsof +L1 \| grep /var/log/remnanode — Xray пишет в удалённый файл	В правиле нет copytruncate: допишите и перезапустите ноду
SignatureDoesNotMatch при проверке	endpoint, region и часы сервера: timedatectl	Сверьте endpoint/region с кабинетом; если часы уехали — включите NTP (timedatectl set-ntp true)
AccessDenied	Права ключа и имя бакета в remote=	Ключ должен иметь доступ к этому бакету; имя бакета пишется без https://
NoSuchBucket	Существует ли бакет и тот ли регион	Создайте бакет в кабинете или поправьте регион

Файлы не уезжают по расписанию	tail /var/log/rclone-logs.log, grep CRON /var/log/syslog	В /etc/cron.d обязателен пользователь (root) после времени, а % экранируется как \%
Потерян пароль шифрования	—	Расшифровать старые файлы невозможно. Создайте новый s3c с новым паролем и сразу сохраните его в менеджер паролей
Чего это не даёт
Логи не спасают от блокировок и не ускоряют ноды — это инструмент разбора, а не защиты.
Ключ с правом удаления на ноде — при взломе или изъятии сервера логи можно стереть. Поэтому ноде — ключ «только загрузка» там, где провайдер это умеет.
Шифрование защищает копию в облаке от провайдера и от утечки одного ключа, но не от изъятия ноды. Пароль шифрования лежит на ноде в rclone.conf в обратимом виде: кто получил сервер, тот расшифрует и облачную копию, если ключ позволяет читать бакет. И свежие логи лежат на сервере открыто, пока не уехали и не удалились ротацией. Для сервера под риском изъятия держите локально минимум (rotate 2) и короткий срок в облаке; полная защита — шифрование открытым ключом (age/gpg), когда нода умеет только зашифровать, а расшифровать может лишь тот, у кого закрытый ключ.
Access-лог не показывает объём трафика по клиенту — это статистика панели, а не лог.
Общий аккаунт на несколько человек лог не разделит: метка email: одна на подписку, кто именно из пользователей виноват, он не скажет.
Бэкап, который ни разу не восстанавливали, — не бэкап: раз в месяц разворачивайте копию из облака на запасном сервере.

Связано: «Мониторинг и бэкап» (дамп БД и Uptime Kuma), «Почему ноды перестают работать» (логи и диск), «Защита панели», «Антиторрент» (откуда берутся жалобы хостеров).

Правило logrotate проверено на logrotate 3.22; команды rclone, шифрование и логи нод сверены с официальной документацией rclone и Remnawave.
