Заголовок: Один хост → тысячи юзеров: масштабирование

Хост в Remnawave — это карточка в панели с одним готовым конфигом для клиента: адрес, порт, протокол, ключи. Клиентское приложение видит хост как один сервер в своём списке. Пока у вас десяток пользователей и один сервер, одного хоста хватает за глаза. Как только пользователей становится сотни, а сервер один — либо он не тянет нагрузку, либо блокировка по адресу этого единственного сервера роняет разом всех.

Здесь — два независимых способа так не жить: 1. Один хост → несколько нод: перед несколькими серверами (в терминологии Remnawave — нодами, это машины, к которым реально подключаются клиенты) ставится балансировщик, и нагрузка размазывается по числу пользователей. 2. Одна нода → несколько транспортов (транспорт — способ упаковки трафика: TCP/gRPC/xHTTP): если один вид трафика зарежут, клиент молча переключится на другой.

Оба приёма опираются на инбаунды (inbound — входная точка на ноде: протокол + порт + настройки, куда стучится клиент) и сквады (squad — группа в панели, которая решает, какие хосты увидят те или иные пользователи). Ошибка на любом шаге обычно выглядит не как «ничего не работает», а как «работает у одних и не работает у других»: например, инбаунд забыли добавить в сквад — и часть пользователей молча не подключится, хотя сервер жив и порт открыт. Такие случаи разобраны в конце статьи, в разделе «Если не получилось».

📖 Незнакомые слова? Все термины простыми словами смотрите в Словаре терминов.

1. Один хост → несколько нод (распределение по юзерам)

Проблема. У хоста один адрес (Address), а нод нужно несколько. Решение — поставить перед нодами L4-балансировщик: отдельную программу (HAProxy или nginx), которая раскидывает входящие соединения по нодам. Метод least-conn отправляет нового клиента туда, где сейчас меньше всего активных соединений, — грубое, но рабочее приближение к «поровну по пользователям». Все ноды при этом держат один и тот же инбаунд с одинаковыми ключами Reality, чтобы клиент, попавший на любую из них, прошёл проверку.

Шаги
В Remnawave создайте один Config Profile (это полный Xray-конфиг ноды, хранится в панели) с одним инбаундом VLESS Reality и включите его на всех нодах N1/N2/N3. Ключ Reality лежит в самом профиле, поэтому он одинаковый у всех нод. Должно получиться: у нод N1, N2, N3 в списке активных инбаундов стоит галочка напротив одного и того же профиля, а не у каждой свой.
Поднимите фронт-балансер (отдельный дешёвый VPS или одна из нод) на порту:443, бэкендами впишите IP нод на их рабочем порту (например 8443, чтобы не конфликтовать с портом фронта). Должно получиться: с балансера каждая нода отвечает на этот порт (хотя бы принимает TCP-соединение).
Заведите Host в панели: Address = домен/IP балансировщика, Inbound = тот самый профиль. Теперь клиент идёт на балансер, а тот раздаёт его по least-conn. Должно получиться: в подписке у клиента один сервер с адресом балансировщика, а не три отдельных.
HAProxy (least-conn, TLS-passthrough, Reality цел)
haproxy
frontend ft
 bind 0.0.0.0:443
 mode tcp
 tcp-request inspect-delay 5s
 tcp-request content accept if { req_ssl_hello_type 1 }
 default_backend pool

backend pool
 mode tcp
 balance leastconn # раздаём по числу активных соединений ≈ по юзерам
 option ssl-hello-chk
 server n1 10.0.0.11:8443 check
 server n2 10.0.0.12:8443 check
 server n3 10.0.0.13:8443 check
 # server n4 10.0.0.14:8443 check backup # горячий резерв (только при падении основных)

Слить ноду без обрыва (рантайм-API):

bash
echo "set server pool/n2 state drain" | socat stdio /var/run/haproxy.sock

nginx stream (альтернатива)
nginx
stream {
 upstream pool { least_conn;
 server 10.0.0.11:8443 max_fails=2 fail_timeout=10s;
 server 10.0.0.12:8443 max_fails=2 fail_timeout=10s;
 server 10.0.0.13:8443; }
 server { listen 443; proxy_pass pool; proxy_connect_timeout 3s; }
}

⚠️ Reality-ключ должен быть один на все ноды за балансером, иначе клиент, попавший на «другую» ноду, не подключится. Для долгих VPN-сессий least-conn лучше round-robin: RR со временем перегрузит ту ноду, кому достались самые долгоживущие сессии. Всё это только для TCP — Hysteria2 (протокол поверх QUIC/UDP) балансируйте отдельно, DNS-записью или сменой порта.

Альтернатива без фронта: сквад-сплит

Без отдельного балансера тоже можно: разделите пользователей по сквадам вручную и дайте каждому скваду свой одно-нодовый хост. Способ грубее — распределение фиксированное, а не по факту нагрузки, — зато не нужен ни балансер, ни его мониторинг. Годится, когда ноды разной мощности: премиальных пользователей осознанно сажаете на мощную ноду, остальных — на обычные.

⚠️ Инбаунд, который не добавлен ни в один сквад, не получает пользователей вообще: их идентификаторы просто не попадают в список клиентов на ноде, и подключение рвётся на самой первой проверке. Снаружи это выглядит так, будто сервер не отвечает, хотя порт открыт и служба жива. Пустая подписка почти всегда означает именно это — пустой или неверный сквад, а не поломку панели.

2. Одна нода → несколько транспортов (TCP / gRPC / xHTTP)

Разные транспорты (способы упаковки трафика) DPI режет по-разному: то, что душит один, может вообще не трогать другой. Поэтому вместо одного канала на ноде держат сразу три инбаунда (все на Reality, каждый на своём порту) и отдают их клиенту тремя хостами. Приложение получит сразу три сервера — TCP, gRPC и xHTTP — и само выберет рабочий, если один из них перестанет отвечать.

Сгенерируйте ключи (один комплект Reality можно переиспользовать на ноде, shortId у каждого инбаунда свой):

bash
xray x25519 # privateKey → сервер, publicKey → клиент
xray uuid # id пользователя
openssl rand -hex 8 # shortId (свой на каждый инбаунд)

🔑 Ключи Reality проще всего сгенерировать прямо в панели. В редакторе конфига Remnawave (кнопка меню рядом с «Форматировать») есть пункт «Сгенерировать ключи» — он сам подставит пару privateKey/publicKey, ничего ставить и вызывать вручную не нужно. Там же есть «Скачать с Github» — подтянуть свежее ядро Xray.

Если нужно получить пару вне панели (например, готовите конфиг заранее), подойдёт любой путь: - на ноде, внутри контейнера: docker exec remnanode xray x25519; - на любой машине, хоть на своём ноутбуке — ключи к серверу не привязаны: wget -qO- https://github.com/XTLS/Xray-core/releases/latest/download/Xray-linux-64.zip | busybox unzip - xray && chmod +x xray && ./xray x25519

privateKey идёт в конфиг ноды, publicKey — на Host в панели.

Как отдать клиенту в Remnawave
В Config Profile ноды пропишите три инбаунда из блока выше (это один массив inbounds, а не три отдельных профиля). Должно получиться: редактор конфига в панели показывает «Xray config is valid».
Включите все три на самой ноде: Nodes → ваша нода → галочки напротив всех трёх инбаундов. Должно получиться: в списке активных инбаундов ноды три строки — TCP, gRPC, xHTTP.
Создайте три Host'а, по одному на инбаунд: Remark «🇩🇪 DE · TCP», «🇩🇪 DE · gRPC», «🇩🇪 DE · xHTTP», Address = домен/IP ноды, Inbound = соответствующий. Порт подтянется из инбаунда сам. Должно получиться: три карточки в списке «Хосты» с одним и тем же адресом, но разными портами и разным Inbound.

С версии 3.4.4 второй и третий хост необязательно собирать с нуля — их можно клонировать из первого (кнопка рядом с хостом) и поменять только Remark и Inbound, либо сразу поправить нужные поля в JSON-редакторе хоста (тоже появился в 3.4.x). Заодно у хоста есть поле Tags (до Remnawave 2.8.0 оно называлось Tag и принимало одно значение, теперь это список): по нему на хост ссылаются другие механизмы панели, например автовыбор и шаблон подписки.

Добавьте все три инбаунда в нужные сквады (сквад не задан — хост не появится в подписке пользователей этого сквада). Должно получиться: на вкладке «Инбаунды» у сквада стоят все три галочки, а у тестового пользователя из этого сквада в подписке видно все три сервера.
Лишние транспорты можно скрыть флагом is_hidden и держать как запас — например, для «Автовыбора» или как скрытый хост-донор, из которого шаблон подписки на самом деле берёт исходящее соединение (подробнее — в статье «Страница подписки»). Должно получиться: скрытый хост не отображается в подписке клиента, но продолжает участвовать в выдаче конфигов.

Так одна нода даёт сразу TCP/gRPC/xHTTP. Если зарезали один транспорт, клиент работает через другой. Это база для «Автовыбора» (см. «Балансировщики»).

Создание хоста (Хосты → +): Примечание, кнопка «Выбрать инбаунд», Адрес и Порт. Поле «Ноды» используется только для визуальной привязки, на выдачу не влияет.
Отпечаток (fingerprint) при создании Host обязателен

При создании Host в Remnawave есть поле Fingerprint (uTLS). Это не косметика: uTLS полностью переписывает TLS-ClientHello под выбранный браузер, чтобы DPI по TLS-отпечатку (JA3) видел «обычный браузер», а не прокси-клиент. Оставлять пустым нельзя: голый Go-отпечаток палится сразу.

⚠️ chrome не ставьте. Это самый массовый отпечаток: по нему в первую очередь и учат DPI-фильтры, а на части сборок Reality-нода с ним вообще не поднимается. По умолчанию ставьте firefox, в ротацию берите qq.

Значение	Когда
firefox ⭐	рекомендуемый по умолчанию. Другой TLS-стек (NSS), реже попадает под chrome-ориентированные фильтры.
qq ⭐	хорошая альтернатива/ротация: нестандартный отпечаток (стек QQ-браузера), который массовые фильтры обычно не трогают.
⛔ chrome	не использовать: самый палевный (по нему учат фильтры), и на части сборок нода с ним не стартует.
safari / ios / android / edge	под конкретную аудиторию/устройства, для разнообразия.
randomized / random	разный отпечаток на сессию, спасает от простых JA3-сигнатур, но «нестабильный» профиль сам по себе бывает заметен.

Практика: - Основной хост: firefox; второй/резервный хост той же ноды: qq. Разные отпечатки = живучесть при волне блокировок. - ⛔️ Не ставьте chrome_pq (post-quantum): он ломает Reality (ошибка nil ecdhe_key). - Если хост «лёг», первым делом смените fingerprint (firefox↔qq) и/или SNI: часто снимает блок без пересоздания ноды.

Где это в панели: Hosts → (ваш хост) → поле Fingerprint. Отпечаток живёт на хосте, а не в inbound: на один inbound можно повесить несколько хостов с разными отпечатками (и так держать ротацию).

Вкладка «Расширенные» карточки Host: поле SNI (ваш домен) и Отпечаток. Выбирайте firefox/qq, держите второй хост той же ноды с другим отпечатком для ротации.
Поле SNI на хосте: трогайте, только если нужна ротация

SNI (Server Name Indication) — имя сайта, которое видно в самом начале TLS-соединения ещё до шифрования; именно по нему DPI понимает, куда вы идёте, и на этом строится вся маскировка Reality. У хоста в панели тоже есть своё поле SNI (вкладка «Расширенные», см. рисунок выше) — но у большинства рабочих хостов оно пустое. Пока оно пустое, панель сама подставляет имя из serverNames того инбаунда, к которому привязан хост. Если вписать в это поле своё значение — оно перекроет serverNames из конфига, и хост будет ходить именно на вписанное имя, что бы вы потом ни поменяли в инбаунде.

Отсюда частая путаница: донора сменили в конфиге ноды, а конкретный хост продолжает стучаться в старый — потому что когда-то на нём руками вписали SNI, и с тех пор его никто не трогал. Если не занимаетесь ротацией доноров по отдельным хостам вручную, полю SNI на хосте лучше оставаться пустым.

Открыть порты на ноде
bash
ufw allow 443/tcp
ufw allow 8443/tcp
ufw allow 2096/tcp
ufw allow from PANEL_IP to any port 2222 proto tcp # node API только с панели

Должно получиться: ufw status показывает все четыре правила, а ss -tlnp sport =:443 (и так же для 8443/2096) — что порт слушает процесс ноды, а не что-то чужое.

С Remnawave 3.4.x к ноде можно зайти по SSH прямо из браузера — кнопка есть в карточке ноды. Для разовой проверки порта или лога отдельный SSH-клиент не нужен.

Чего это не решает
Балансировщик — сам по себе ещё одна точка отказа. Заблокируют его адрес — ляжет вся группа нод разом, хотя каждая нода в отдельности жива. Держите резерв и на него.
least-conn считает соединения, а не реальную нагрузку. Мощная и слабая нода получат клиентов примерно поровну, хотя тянут они по-разному. Если ноды разной мощности, лучше сквад-сплит с ручным распределением.
Общий Reality-ключ на всех нодах — это компромисс. Он и даёт балансировку, и означает, что утечка ключа с одной ноды компрометирует все остальные разом.
Балансировка в этой схеме — только для TCP. Hysteria2 поверх UDP она не покрывает, для него нужна отдельная схема (DNS или смена порта).
Несколько транспортов не спасают от блокировки самого адреса ноды. Они спасают от блокировки конкретного вида трафика. Забанят IP — упадут все три инбаунда одновременно, потому что это один и тот же сервер.
