Заголовок: VLESS-XHTTP (Reality / за CDN)

Что это. XHTTP (раньше назывался SplitHTTP) — транспорт: способ упаковать VPN-трафик перед отправкой, от которого зависит, насколько устойчиво соединение к блокировкам. Он пришёл на замену старому транспорту на WebSocket и работает стабильнее. Главное отличие от остальных вариантов — XHTTP дружит с CDN (чужой сетью серверов-посредников вроде Cloudflare) и остаётся рабочим, даже когда блокируют не протокол, а сам IP-адрес сервера.

Что получится. Один из двух готовых конфигов: прямой (Вариант A, Reality без своего домена) или через CDN (Вариант B, со своим доменом и TLS). Подставьте свои данные и вставьте профиль в панель.

Сколько времени. Ключи и домен уже готовы — 10–15 минут. Поднимаете CDN и сертификат с нуля — рассчитывайте на полчаса-час, большая часть уйдёт на ожидание сертификата и настройку CDN-провайдера.

Кому нужно. Тем, у кого блокируют IP-адрес сервера, и тем, кто хочет спрятать ноду за CDN. Если у вас блокируют не адрес, а сам протокол, быстрее и стабильнее взять обычный VLESS-Reality или Selfsteal (см. «Какой протокол выбрать») — без CDN ниже задержка и меньше шагов настройки.

У XHTTP нет параметра flow (это надстройка вроде Vision, которая довешивается к обычному TCP-Reality) — в конфигах ниже это поле просто отсутствует, так и должно быть.

Шаг 1: сгенерируйте ключи Reality (только для Варианта A)

Нужны, если собираете Вариант A (прямой Reality без CDN). Сразу идёте за CDN — эта пара ключей не понадобится, переходите к шагу 2.

bash
xray x25519 # privateKey → в конфиг, publicKey → на Host
openssl rand -hex 8 # shortId

Должно получиться: xray x25519 выведет два ключа — приватный (идёт в конфиг ноды) и публичный (идёт на Host в панели). openssl rand -hex 8 выведет строку из 16 символов hex — это shortId.

🔑 Ключи Reality проще всего сгенерировать прямо в панели. В редакторе конфига Remnawave (кнопка меню рядом с «Форматировать») есть пункт «Сгенерировать ключи» — он сам подставит пару privateKey/publicKey, ничего ставить и вызывать вручную не нужно. Там же есть «Скачать с Github» — подтянуть свежее ядро Xray.

Если нужно получить пару вне панели (например, готовите конфиг заранее), подойдёт любой путь: - на ноде, внутри контейнера: docker exec remnanode xray x25519; - на любой машине, хоть на своём ноутбуке — ключи к серверу не привязаны: wget -qO- https://github.com/XTLS/Xray-core/releases/latest/download/Xray-linux-64.zip | busybox unzip - xray && chmod +x xray && ./xray x25519

privateKey идёт в конфиг ноды, publicKey — на Host в панели.

Шаг 2: придумайте путь XHTTP

Путь — обычный URL-путь, по которому клиент стучится к вашей ноде, как адрес страницы на сайте. Правильного значения не существует, придумываете сами.

Составьте путь по правилам: начинается со слеша, только латиница и цифры (можно дефис и подчёркивание), без пробелов и кириллицы. Пример: /xh.

Должно получиться: короткая строка вида /xh. Её же укажите в обоих профилях ниже и в Host.

Главное правило: путь должен совпадать в трёх местах — в инбаунде (inbound, «входная точка» на ноде: связка протокол + порт + настройки, куда стучится клиент), в Host в панели и в конфиге у клиента. Разошлось хоть в одном символе, включая слеш в конце, — подключения не будет, причём без внятной ошибки: клиент просто не соединится.

Что выбрать. Берите неприметное, похожее на обычный сайт или служебный API:

Хорошо	Плохо
/xh, /assets/track, /api/v2/sync	/vless, /vpn, /xray, /proxy

Разница практическая: по второму столбцу вас находит любой автоматический сканер, который перебирает известные пути прокси. Первый столбец в логах выглядит как обращение к обычному сайту.

⚠️ Путь — это не пароль. Он лежит открытым в конфиге у каждого клиента, и любой, у кого есть подписка, его видит. Путь нужен для маскировки и для того, чтобы развести несколько инбаундов на одном порту, но доступ он не защищает — за это отвечают ключи.

Если нода за CDN: проверьте, что CDN отдаёт этот путь как есть — не кеширует его и не переписывает. Иначе трафик до ноды не дойдёт, а выглядеть будет как «сервер не отвечает». Подробности по каждому провайдеру — в «Спрятать сервер за CDN».

Путь можно сменить и позже, но он прописан в конфигах у клиентов: смена означает обновление подписки у всех. Поэтому выбирайте сразу и не трогайте без причины.

Вариант A: XHTTP-Reality (прямой, без своего серта)

Тот же стелс, что у обычного Reality — соединение маскируется под чужой настоящий сайт, — только транспортом служит XHTTP вместо обычного TCP. Подходит для прямого подключения, без CDN: домен и сертификат не нужны.

Ниже — инбаунд (inbound, «входная точка» на ноде: связка протокол + порт + настройки, куда стучится клиент) с Reality поверх XHTTP. В realitySettings поля target и serverNames указывают на донора — чужой сайт, под чьё TLS-рукопожатие маскируется соединение. serverNames — это и есть SNI (Server Name Indication, «имя сервера»): имя сайта, которое передаётся открытым текстом в самом начале TLS-соединения, ещё до включения шифрования, и по которому DPI обычно определяет, куда вы идёте.

js
{
 "log": { "loglevel": "none" },
 "inbounds": [
 {
 "tag": "vless-xhttp-reality",
 "listen": "0.0.0.0",
 "port": 443,
 "protocol": "vless",
 "settings": { "clients": [], "decryption": "none" },
 "sniffing": { "enabled": true, "destOverride": ["http", "tls", "quic"] },
 "streamSettings": {
 "network": "xhttp",
 "security": "reality",
 "xhttpSettings": {
 "path": "XHTTP_PATH",
 "mode": "auto"
 },
 "realitySettings": {
 "show": false,
 "target": "your-donor.de:443",
 "serverNames": ["your-donor.de"],
 "privateKey": "PRIVATE_KEY_X25519",
 "shortIds": ["REALITY_SHORT_ID"]
 }
 }
 }
 ],
 "outbounds": [
 { "tag": "DIRECT", "protocol": "freedom" },
 { "tag": "BLOCK", "protocol": "blackhole" }
 ],
 "routing": { "rules": [
 { "ip": ["geoip:private"], "outboundTag": "BLOCK" },
 { "domain": ["geosite:category-ads-all"], "outboundTag": "BLOCK" },
 { "protocol": ["bittorrent"], "outboundTag": "BLOCK" }
 ]}
}

Вариант B: XHTTP-TLS (для CDN / Cloudflare)

Честный TLS на вашем домене: сертификат стоит либо у вас на ноде, либо шифрование терминирует сам CDN. Этот вариант годится для фронта за CDN (Cloudflare и другие).

CDN — это сеть чужих серверов-точек входа, их называют эдж (edge, «край»): они физически ближе к пользователю и первыми принимают соединение. Сама точка входа вашу ноду не хранит, она пересылает запрос дальше — на настоящий сервер, который в этой схеме называют ориджин (origin, «источник»). Снаружи виден только адрес эджа, то есть CDN, а реальный IP ноды-ориджина скрыт. Это и защищает от блокировки по адресу.

js
{
 "log": { "loglevel": "none" },
 "inbounds": [
 {
 "tag": "vless-xhttp-tls",
 "listen": "0.0.0.0",
 "port": 443,
 "protocol": "vless",
 "settings": { "clients": [], "decryption": "none" },
 "sniffing": { "enabled": true, "destOverride": ["http", "tls", "quic"] },
 "streamSettings": {
 "network": "xhttp",
 "security": "tls",
 "xhttpSettings": {
 "host": "your.domain",
 "path": "XHTTP_PATH",
 "mode": "auto"
 },
 "tlsSettings": {
 "serverName": "your.domain",
 "alpn": ["h2", "http/1.1"],
 "certificates": [
 {
 "certificateFile": "/etc/letsencrypt/live/your.domain/fullchain.pem",
 "keyFile": "/etc/letsencrypt/live/your.domain/privkey.pem"
 }
 ]
 }
 }
 }
 ],
 "outbounds": [
 { "tag": "DIRECT", "protocol": "freedom" },
 { "tag": "BLOCK", "protocol": "blackhole" }
 ],
 "routing": { "rules": [
 { "ip": ["geoip:private"], "outboundTag": "BLOCK" },
 { "domain": ["geosite:category-ads-all"], "outboundTag": "BLOCK" },
 { "protocol": ["bittorrent"], "outboundTag": "BLOCK" }
 ]}
}

Режимы mode: auto (сам подберёт подходящий), packet-up (данные от клиента к серверу идут отдельными короткими запросами — переживает капризные CDN, которые не любят держать долгий поток на приём), stream-up (данные идут одним непрерывным потоком — быстрее, но проходит не через все CDN). За Cloudflare включите проксирование (оранжевое облако) и тот же path.

Host в Remnawave

Сам конфиг клиентам панель собирает автоматически, но параметры подключения задаются на Host. Впишите туда:

text
Address: your.domain (Reality: IP/домен ноды; CDN: домен CDN)
Port: 443
SNI / Host: your.domain (Reality-вариант — your-donor.de)
path: XHTTP_PATH
publicKey: REALITY_PUBLIC_KEY (только для Варианта A — Reality)
shortId: REALITY_SHORT_ID (только для Варианта A — Reality)
flow: (пусто — у XHTTP нет Vision)
fingerprint: firefox

Грабли

За CDN кеш по этому пути выключите, разрешите методы GET и POST. Подробно по каждому CDN, включая Яндекс, у которого работает только GET, — в «Спрятать сервер за CDN».
Хотите использовать вместо чужого донора свой собственный сайт на ноде (Selfsteal-вариант XHTTP, где target — ваш локальный сайт) — это отдельная схема, смотрите «Профили подключений → §6».

Чего XHTTP не даёт
Не спасает мгновенно, если блокируют не адрес, а сам транспорт. XHTTP защищает от блокировки по IP через CDN, но если под конкретный DPI научатся находить именно XHTTP-паттерн, транспорт придётся менять — это редкий, но не невозможный случай.
CDN добавляет задержку. Обычно 0,2–0,5 секунды к отклику — заметно в играх и голосовых звонках, для обычного сёрфинга не критично.
CDN видит объём вашего трафика, хоть и не содержимое (оно зашифровано). Полной анонимности от CDN-провайдера это не даёт.
iOS хуже дружит с большими буферами XHTTP. На iPhone соединение может рваться там, где на Android с тем же конфигом всё стабильно.
Путь и режимы нужно подбирать под конкретный CDN. Разные провайдеры по-разному относятся к GET/POST, кешированию и режиму packet-up/stream-up — единой настройки на все CDN нет, приходится сверяться с инструкцией по конкретному провайдеру.
Reality-вариант (A) не защищает от блокировки по адресу — тот же принцип, что у обычного Reality: транспорт прячет, как выглядит трафик, а не куда он идёт.
